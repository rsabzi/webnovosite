# نوین وب — وب‌سایت برند شخصی (Webnovo)

سایت چندصفحه‌ای فارسی (RTL) با Next.js 16 / React 19 / Tailwind 4، شامل نمونه‌کارها،
محاسبه‌گر صرفه‌جویی، شبیه‌ساز گردش کار و فرم تماسی که پیام‌ها را **واقعاً و لحظه‌ای**
به تلگرام ارسال می‌کند.

## صفحات

| مسیر | توضیح |
|---|---|
| `/` | صفحه اصلی: جایگاه برند، خدمات، نمونه‌کارها، ROI |
| `/services` | سه خدمت اصلی با مسئله/خروجی/مدل همکاری |
| `/projects` | فهرست فیلترشونده نمونه‌کارهای واقعی |
| `/projects/[slug]` | صفحه اختصاصی هر پروژه |
| `/case-studies` | مطالعات موردی |
| `/automation-check` | ابزار رایگان تشخیص اتوماسیون (فرم ۸ مرحله‌ای + تحلیل سروری + صفحه‌ی نتیجه) |
| `/calculator` | محاسبه‌گر صرفه‌جویی و بازگشت سرمایه |
| `/live-demo` | شبیه‌ساز زنده گردش کار |
| `/pricing` | پلن‌ها و تعرفه |
| `/about` | مسیر برند و متدولوژی |
| `/faq` | سوالات پرتکرار کارفرمایان |
| `/contact` | فرم درخواست مشاوره پروژه |
| `/admin/analytics` | داشبورد محرمانه مدیریت آمار بازدید، تفکیک دستگاه‌ها، صفحات پربازدید و مراجع ورودی |

## راه‌اندازی محلی

```bash
npm install
cp .env.example .env.local   # مقادیر را پر کنید
npm run dev
```

## اتصال فرم تماس به ربات تلگرام

1. در تلگرام به [@BotFather](https://t.me/BotFather) پیام بدهید و با `/newbot` یک ربات بسازید؛ توکن را کپی کنید.
2. آیدی عددی خودتان را از [@userinfobot](https://t.me/userinfobot) بگیرید.
3. **یک‌بار به ربات خودتان `/start` بزنید** (تلگرام اجازه نمی‌دهد ربات به کسی که شروع نکرده پیام بدهد).
4. متغیرها را تنظیم کنید:

```env
TELEGRAM_BOT_TOKEN=123456:AA...
TELEGRAM_CHAT_ID=6912564436        # چند مقصد با کاما: 111,222
DATABASE_URL=                       # اختیاری
```

## ابزار «تشخیص رایگان اتوماسیون» (`/automation-check`)

قیف اصلی جذب لید سایت: کاربر در هشت گام کوتاه وضعیت کسب‌وکارش را می‌گوید و بلافاصله
تحلیل اولیه می‌گیرد. مسیر فنی به این شکل است:

1. **فرم چندمرحله‌ای (کلاینت)** — پاسخ‌ها در `sessionStorage` ذخیره می‌شوند، بنابراین رفرش
   نه اطلاعات را از بین می‌برد و نه صفحه را خراب می‌کند. هیچ فراخوانی AI پیش از Submit انجام نمی‌شود.
2. **`POST /api/automation-check` (سرور)** — اعتبارسنجی ورودی، محدودیت نرخ، تحلیل، و اعلان تلگرام.
3. **تحلیل** با Google Gemini از طریق `GEMINI_API_KEY` (فقط سمت سرور؛ هیچ کلیدی در باندل
   کلاینت نیست). خروجی مدل با `responseSchema` به JSON ساختاریافته محدود و سپس در سرور
   اعتبارسنجی/کلمپ می‌شود. اگر کلید تنظیم نباشد یا فراخوانی شکست بخورد (تایم‌اوت، پاسخ خالی،
   JSON نامعتبر)، تحلیل **قاعده‌محور** جایگزین می‌شود و کاربر همچنان نتیجه‌ی کامل می‌بیند.
4. **صفحه‌ی نتیجه** شامل فرصت‌های اتوماسیون (عنوان، اهمیت، پیچیدگی، راه‌حل)، گام بعدی پیشنهادی،
   و در صورت لزوم یک ارزیابی صادقانه («اتوماسیون گسترده فعلاً اولویت شما نیست») است.

### متغیرهای محیطی تحلیل AI

```env
GEMINI_API_KEY=            # از https://aistudio.google.com/apikey
GEMINI_MODEL=              # خالی = انتخاب خودکار جدیدترین مدل متنی فلشِ در دسترس کلید
GEMINI_THINKING_LEVEL=low  # فقط مدل‌های نسل ۳
GEMINI_API_BASE_URL=       # فقط برای تست محلی؛ روی سرور تنظیم نکنید
```

### انتخاب مدل و پایداری آن

گوگل دسترسی پروژه‌های جدید به مدل‌های سری ۲.۵ را محدود کرده است
(پاسخ `404` با پیام «no longer available to new users») و برای پروژه‌های جدید
`gemini-3.8-flash` را پیشنهاد می‌کند. کد این موضوع را خودکار مدیریت می‌کند:

1. **انتخاب خودکار مدل:** اگر مدل تنظیم‌شده در دسترس نباشد، فهرست واقعی مدل‌های همین
   کلید از `GET /v1beta/models` خوانده می‌شود و جدیدترین مدل متنی فلشِ موجود انتخاب می‌شود.
2. **زنجیره‌ی جایگزین:** اگر انتخاب خودکار ممکن نباشد، مدل‌ها به‌ترتیب
   `gemini-3.8-flash → 3.7 → 3.6 → 3.5 → 3.5-flash-lite → 2.5-flash` امتحان می‌شوند.
3. **تفکیک نسل‌ها در پارامتر تفکر:** نسل ۳ از `thinkingConfig.thinkingLevel` استفاده می‌کند و
   نسل ۲.۵ از `thinkingConfig.thinkingBudget`؛ ارسال پارامتر اشتباه خطای `400` می‌دهد و
   کد بر اساس نسل مدل، پارامتر درست را می‌فرستد.
4. **دو قالب خروجی ساختاریافته:** ابتدا `responseMimeType + responseSchema` و در صورت
   رد شدن توسط مدل، `responseFormat.text.{mimeType,schema}` امتحان می‌شود.
5. **اوج تقاضا (۵۰۳ «high demand») و محدودیت نرخ (۴۲۹):** مدلِ پرظرفیت ۶۰ ثانیه کنار گذاشته
   می‌شود و درخواست به مدل دیگری در همان لحظه می‌رود (چرخش روی حداکثر ۳ مدل در هر فراخوانی،
   با احترام به هدر `Retry-After` گوگل). بنابراین یک مدل شلوغ باعث از دست رفتن تحلیل نمی‌شود.
6. **مدل‌های بازنشسته سهمیه نمی‌خورند:** مدلی که با `404` پاسخ می‌دهد (بازنشسته/ناموجود)
   هزینه‌ی سهمیه‌ی «حداکثر ۳ مدل» را مصرف نمی‌کند و کد سراغ مدل بعدی می‌رود؛ کلیدهایی که
   چند مدل نسل ۲.۵ در دسترس ندارند، به اشتباه روی تحلیل قاعده‌محور نمی‌افتند. مدل‌های نسل ۲.۵
   هم فقط به‌عنوان آخرین گزینه امتحان می‌شوند.
7. **تلاش مجدد:** خطاهای گذرا (شبکه/۵xx/پاسخ خالی) تا ۳ بار با بودجه‌ی زمانی ۲۶ ثانیه تکرار
   می‌شوند و تنها در شکست کامل، تحلیل قاعده‌محور (با نشان صریح روی صفحه‌ی نتیجه) جایگزین می‌شود.
   در آن حالت، کاربر با یک کلیک و بدون پر کردن دوباره‌ی فرم می‌تواند «تحلیل هوش مصنوعی» را
   دوباره درخواست کند.

بررسی سلامت پیکربندی روی سرور (بدون افشای کلید): `GET /api/automation-check?probe=1`

### فعال‌سازی تحلیل اختصاصی با هوش مصنوعی (روی Vercel)

تحلیل AI **فقط زمانی فعال می‌شود که کلید در متغیرهای محیطی سرور باشد**. اگر کلید نباشد
(یا فراخوانی مدل در آن لحظه شکست بخورد)، سیستم به تحلیل قاعده‌محور برمی‌گردد و همین موضوع
روی صفحه‌ی نتیجه هم صریح به کاربر نشان داده می‌شود.

۱) کلید را از <https://aistudio.google.com/apikey> بگیرید.
۲) در Vercel → Project → **Settings → Environment Variables** این‌ها را برای
   **Production و Preview** بسازید و بعد **Redeploy** کنید:

| نام | مقدار | توضیح |
|---|---|---|
| `GEMINI_API_KEY` | کلید شما | **الزامی برای فعال شدن AI.** فقط سرور؛ هرگز commit نشود |
| `GEMINI_MODEL` | خالی بگذارید | اختیاری؛ اگر خالی باشد کد خودش جدیدترین مدل متنی فلشِ در دسترس کلید را پیدا می‌کند |
| `GEMINI_THINKING_LEVEL` | `low` | اختیاری (فقط مدل‌های نسل ۳): `low` \| `medium` \| `high` |
| `NEXT_PUBLIC_SITE_URL` | `https://www.webnovo.ir` | برای canonical/sitemap/OG |
| `LEADS_ADMIN_TOKEN` | یک رشته‌ی تصادفی | برای `GET /api/leads` و `/api/telegram/setup` |

> ⚠️ `GEMINI_API_BASE_URL` را روی سرور تنظیم نکنید؛ فقط برای تست محلی (پروکسی/شبیه‌ساز) است.

۳) بعد از دیپلوی، سلامت را تأیید کنید:

```bash
curl -s "https://www.webnovo.ir/api/automation-check?probe=1"
```

پاسخ نمونه (سالم):

```json
{
  "ok": true,
  "provider": "google-gemini",
  "model": "gemini-2.5-flash",
  "error": null,
  "environment": "production",
  "branch": "main",
  "commit": "a69e207",
  "keyPresent": true,
  "keyLooksValid": true,
  "hint": "پیکربندی هوش مصنوعی سالم است؛ تحلیل‌ها با مدل انجام می‌شود."
}
```

`environment` و `commit` نشان می‌دهند کدام محیط اجرا و کدام کامیت در حال سرویس‌دهی است — برای
اطمینان از اینکه متغیر را در جای درست گذاشته‌اید و دیپلوی جدید انجام شده است.

> ⚠️ **دام رایج:** در Vercel هر متغیر برای محیط‌های مشخصی (`Production` / `Preview` / `Development`)
> تعریف می‌شود. اگر کلید را فقط برای `Preview` بسازید، سایت اصلی (Production) همچنان قاعده‌محور
> می‌ماند. مقدار را برای **همان محیطی که دامنه روی آن سرویس می‌دهد** (معمولاً Production) هم فعال کنید
> و بعد **Redeploy** بزنید؛ متغیرهای محیطی روی دیپلوی‌های ساخته‌شده‌ی قبلی اثری ندارند.

**عیب‌یابی سریع**

| نشانه | علت محتمل | کار |
|---|---|---|
| نشان «تحلیل قاعده‌محور» روی نتیجه | کلید تنظیم نشده **یا فقط برای محیط دیگر تنظیم شده** | `probe` را بزنید؛ اگر `keyPresent:false` بود کلید را برای همان `environment` بسازید (Production و Preview) و Redeploy کنید |
| `probe` می‌گوید `keyPresent:false` با `environment:"production"` | کلید فقط در Preview ساخته شده | ویرایش متغیر → تیک `Production` (و `Preview`) → Save → Redeploy |
| `probe` می‌گوید `keyLooksValid:false` | کلید با کوتیشن/فاصله ذخیره شده یا کلید AI Studio نیست | مقدار را دوباره از AI Studio کپی کنید (بدون کوتیشن، یک رشته‌ی پیوسته، شروع با `AIza`) |
| `probe` می‌گوید `HTTP 400/401/403` | کلید نامعتبر/محدود | کلید را از AI Studio تازه کنید |
| `probe` می‌گوید `HTTP 404 … no longer available to new users` | مدل انتخابی برای کلیدهای جدید بازنشسته شده | `GEMINI_MODEL` را خالی بگذارید (انتخاب خودکار) یا `gemini-3.8-flash` قرار دهید |
| نتیجه با نشان «قاعده‌محور» و علت `503 high demand` | مدل‌ها در آن لحظه در اوج تقاضا بودند | کد خودکار روی مدل بعدی می‌چرخد؛ اگر باز هم شد، کاربر می‌تواند از دکمه‌ی «تلاش دوباره برای تحلیل هوش مصنوعی» استفاده کند |
| `probe` می‌گوید `fetch failed` | دسترسی خروجی سرور به Google بسته است | `GEMINI_API_BASE_URL` نباید تنظیم باشد (فقط برای تست محلی است) |
| `commit` قدیمی است | دیپلوی جدید ساخته نشده | بعد از تغییر متغیرها حتماً Redeploy کنید |

در هر خطای گذرا، سیستم خودش تا ۳ بار (با بودجه‌ی زمانی ۲۶ ثانیه) تلاش دوباره می‌کند و تنها در
صورت شکست کامل به تحلیل قاعده‌محور برمی‌گردد؛ کد `maxDuration = 30` در مسیر API همین را تضمین می‌کند.

### مسیرهای مدیریتی

- `GET /api/leads` فقط با هدر `x-admin-token` برابر با `LEADS_ADMIN_TOKEN` در دسترس است؛
  اگر این متغیر تنظیم نشده باشد، مسیر عمداً `404` برمی‌گرداند تا هیچ اطلاعات تماس مشتری
  به‌صورت عمومی خواندنی نباشد.

پیام‌ها از `/api/leads` (فرم درخواست پروژه) و `/api/calculator` (وقتی کاربر شماره تماس بگذارد) ارسال می‌شوند.

### پیدا کردن `TELEGRAM_CHAT_ID` بدون ابزار اضافه

پس از تنظیم `TELEGRAM_BOT_TOKEN` و دیپلوی:

1. در تلگرام به ربات خود (`@testingwebnvobot`) پیام `/start` بدهید.
2. آدرس `https://<دامنه-شما>/api/telegram/setup` را در مرورگر باز کنید — عدد `chat_id` نمایش داده می‌شود.
3. آن عدد را در `TELEGRAM_CHAT_ID` بگذارید و دوباره دیپلوی کنید.
4. برای تست نهایی یک درخواست `POST` به همان آدرس بزنید تا پیام آزمایشی در تلگرام دریافت کنید:
   `curl -X POST https://<دامنه-شما>/api/telegram/setup`

> پس از تنظیم `TELEGRAM_CHAT_ID`، این مسیر دیگر فهرست چت‌ها را نشان نمی‌دهد.

سلامت سرویس: `GET /api/health` وضعیت دیتابیس و تنظیم‌بودن تلگرام را برمی‌گرداند.

> نکته امنیتی: توکن ربات فقط سمت سرور استفاده می‌شود و هرگز داخل کد فرانت‌اند قرار نمی‌گیرد.

## انتشار روی Vercel

1. مخزن را در Vercel ایمپورت کنید. دیپلوی به مقدار **Root Directory** وابسته نیست
   و هر دو حالت کار می‌کند (توضیح در بخش «پیکربندی Vercel» پایین).
2. در بخش **Environment Variables** مقادیر `TELEGRAM_BOT_TOKEN` و `TELEGRAM_CHAT_ID`
   و در صورت نیاز `DATABASE_URL` و `NEXT_PUBLIC_SITE_URL` را وارد کنید.
3. Deploy. مسیرهای `robots.txt` و `sitemap.xml` به‌صورت خودکار تولید می‌شوند.

دیتابیس اختیاری است؛ اگر `DATABASE_URL` خالی باشد سایت بدون خطا بالا می‌آید و
درخواست‌ها فقط از مسیر تلگرام تحویل داده می‌شوند.

### پیکربندی Vercel (دو فایل `vercel.json`)

Vercel فقط **یک** `vercel.json` را می‌خواند: همانی که داخل پوشهٔ Root Directory
پروژه قرار دارد. به همین دلیل دو فایل داریم و هر کدام فقط در یک حالت استفاده می‌شود:

| Root Directory در داشبورد | فایلی که خوانده می‌شود | نحوهٔ بیلد |
| --- | --- | --- |
| `webnovo-portofolio` | `webnovo-portofolio/vercel.json` | دستورها از داخل همین پوشه اجرا می‌شوند (`npm ci` و `npm run build`) |
| خالی (ریشهٔ ریپو) | `vercel.json` ریشه | `builds` مستقیم `@vercel/next` را روی `webnovo-portofolio/package.json` اجرا می‌کند |

قواعد مهم:

- داخل هیچ‌کدام از این دو فایل از `cd webnovo-portofolio` استفاده نکنید. وقتی Root
  Directory روی این پوشه باشد، دستورها از قبل داخل آن اجرا می‌شوند و `cd` شکست می‌خورد.
- در حالت ریشه، `builds` تنظیمات Build/Install/Output داشبورد را نادیده می‌گیرد.
  در حالت زیرپوشه هم مقادیر `webnovo-portofolio/vercel.json` روی تنظیمات داشبورد اولویت دارند.
  پس مقدارهای قدیمی یا اشتباه داشبورد بیلد را نمی‌شکنند.
- `npm ci` از `package-lock.json` نصب می‌کند. بعد از تغییر وابستگی‌ها حتماً lockfile را هم commit کنید.
